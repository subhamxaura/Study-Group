# Study-Group REST API Reference

This reference synthesizes the supplied route inventories. It documents observed handler behavior, not an inferred product contract. Route paths are shown literally; bracketed segments are dynamic path parameters. “No explicit validation” means the inventory did not establish a route-level format check; it does not promise acceptance by downstream storage. Unless stated otherwise, error statuses below are observed or mapped by the shared wrapper.

## Request, response, and authentication conventions

- **Session:** Most protected routes require the `sg_session` JWT cookie. `lib/auth.ts` signs/verifies it with `JWT_SECRET` (configuration requires at least 32 UTF-8 bytes); default expiry is seven days. Cookie options are `HttpOnly`, `SameSite=Lax`, `path=/`, and `Secure` only in production. `withUser` resolves the cookie to an existing database user and returns 401 if none is resolved. `withRoute` does not impose authentication. Middleware's cookie-presence check on matched pages is not API authorization.
- **Passwords and safe users:** Registration and login use `bcryptjs` with hash cost 12. Authentication responses use `toSafeUser`, not password hashes, and include only fields mapped there.
- **Envelope:** Shared API helpers commonly return success as `{ok:true,data:...}` and failure as `{ok:false,error:...}`. Route inventories describe endpoint payloads below; do not infer additional fields beyond those described. `/api/health` is an explicit exception and returns raw health JSON. Login throttling and AI/quiz limit responses may include `retryAfter` seconds.
- **Common errors:** `parseBody` maps malformed JSON to 400; shared Zod validation errors map to 422; `AuthError` keeps its declared status (including helper-generated 403s); unexpected caught errors are generic 500s without infrastructure detail. Not every handler uses `parseBody` or defines a route-specific error. A status not listed for a route should not be treated as an exhaustive guarantee.
- **Rate limits:** Login uses an in-memory sliding window of 10 attempts per five minutes per derived client IP. AI chat is 20/user/5 minutes, quiz generation 10/user/5 minutes, and quiz submission 30/user/5 minutes. Those Next.js application limits remain process-local, not distributed: serverless instances have separate windows. Login's client key derives from the first `x-forwarded-for` value, then `x-real-ip`, then `local`. Separately, the persistent realtime companion enforces Redis-backed atomic counters for WebSocket upgrades, ticket authentication, message-event publishing, and typing; deployment defaults and overrides are documented below and in `.env.example`.
- **Cookie/CSRF:** The session cookie is `SameSite=Lax`. Authenticated API requests are rejected when Fetch Metadata says `cross-site`, or a supplied `Origin`/`Referer` does not match the request origin. Requests without those headers remain supported for non-browser clients; no synchronizer CSRF token is used.

**Group boundary and ambiguity notes (preserved from inventory):**

- `lib/groups.ts` establishes role order MEMBER < ADMIN < OWNER; `requireMembership` and `requireRole` throw 403. Route-level checks are important boundaries: private-group contents and group chat/member APIs are membership-gated, while public group detail and unauthenticated invite preview are intentionally more exposed by these handlers.
- Invitation preview is unauthenticated and the 43-character random code functions as a bearer capability; acceptance still requires a logged-in user. Invite creation/revocation is restricted to ADMIN/OWNER, and revocation is scoped to the route's group and pending status.
- Message replies are constrained to existing non-deleted parent messages in the same group. before/since/vsince and most path IDs still lack explicit format validation. No behavior beyond handler/helper/database code is assumed.
- Group listing's visibility=private branch explicitly restricts results to caller membership; mine=1 is likewise member-scoped. However size is filtered after page retrieval while total is computed before size filtering, and activity is converted numerically without enforcing documented 7d/30d choices.
- The sync route keeps typing presence in process-local memory, not shared persistence; its GET returns group member identifiers and message deltas only after membership authorization. POST typing payload is not schema-validated and malformed JSON is treated as an empty object, which marks the caller as typing.

### Optional WebSocket transport

The persistent Node companion accepts browser connections at `/ws` only from `REALTIME_ALLOWED_ORIGINS`. The client first obtains `POST /api/realtime/tickets` and sends `{type:"auth",ticket}` as its first text frame; a successful connection receives `ready`, followed by room-scoped `presence` and `typing` frames. Clients may send `{type:"typing",active:boolean}` and a lightweight `ping`; the service returns `pong`. After a persisted chat message/edit/delete/reaction/pin, the Next.js API posts a signed minimal `messages.changed` invalidation. It carries groupId/actorId/time only—never message content. The client then fetches authoritative deltas from `GET /api/groups/[id]/sync`.

Tickets are HS256 JWTs scoped to one user/group, issuer/audience constrained, valid for 60 seconds to establish a connection, and atomically consumed once through shared Redis state. Ticket expiration does not terminate an already authenticated socket. The service validates group membership at connect and periodically thereafter, uses strict origin allowlisting, caps client frames at 2 KiB, and keeps presence/typing ephemeral in expiring Redis leases. Lua-backed fixed-window counters are shared across service replicas: defaults are 300 upgrades/IP/minute, 60 authentication attempts/IP/minute, 6 typing frames per group/user/second, 6,000 signed publishes/IP/minute, and 120 signed publishes/actor/minute. `/publish` is server-to-server and requires a timestamped HMAC-SHA256 signature. Its Redis-published invalidations contain no message content. The companion's `GET /livez` is process liveness; `GET /healthz` is readiness and returns 503 if its Redis command or Pub/Sub connection is not ready. These are companion-service endpoints, not Next.js `/api` routes. When the companion or Redis is absent, clients continue using REST sync (2.5 seconds while visible/8 seconds hidden); connected clients still reconcile every 30/60 seconds.

**Deployment scaling:** multiple realtime service instances can share one Redis endpoint and `REALTIME_REDIS_PREFIX`; session stickiness is not required. Pub/Sub is best-effort and is not a durable event log, so clients must keep using authorized REST delta sync to recover missed notifications. If either Redis connection is unready, `/healthz` returns 503, new upgrades receive 503, and existing sockets close on the next maintenance check (about one second); PostgreSQL and REST remain the durable source of truth.
